1. Creating a custom middleware
*************************************************************************************************************

public class LoggingMiddleware
{
    private readonly RequestDelegate _next;

    public LoggingMiddleware(RequestDelegate next)
    {
        _next = next;
    }

    public async Task Invoke(HttpContext context)
    {
        Console.WriteLine("Request Started");

        await _next(context);

        Console.WriteLine("Request Finished");
    }
}

Register it:
-------------------
app.UseMiddleware<LoggingMiddleware>();
This behaves exactly like the inline app.Use(...) example, but keeps your Program.cs clean.

One-line summary
-----------------------
Middleware is a chain of request-processing components. Each middleware gets a chance to inspect or modify the request,
decide whether to continue by calling next(), and optionally inspect or modify the response on its way back.

A mental model you can keep
---------------------------------
Think of a restaurant order:

Customer
   ↓
Host
   ↓
Waiter
   ↓
Kitchen
   ↓
Chef
Host (Middleware 1): "Welcome! Do you have a reservation?" (logging/checks)
Waiter (Middleware 2): "Here's the menu." (authentication/authorization)
Kitchen (Middleware 3): "Prepare the food." (routing to your endpoint)
Chef (Controller/Endpoint): Actually cooks the meal and returns it.

The meal then travels back through the same chain:

Chef
↑
Kitchen
↑
Waiter
↑
Host
↑
Customer

Each person can still add something before it reaches the customer—for example, the waiter can garnish the plate or the host can thank the customer. That's exactly how the response flows back through the middleware pipeline.

ASP.NET automatically wires up each middleware's _next delegate so every middleware knows who comes after it.

Why is _next a delegate and not a middleware object?

This is a subtle but elegant design choice.

If _next were a concrete middleware class, every middleware would need to know the exact type of the next middleware:

Logging -> Authentication -> Authorization

That would tightly couple them.

Instead, _next is just "something I can call to continue processing."

await _next(context);

Logging doesn't know who is next. It doesn't care whether it's Authentication, Authorization, Routing, or some custom middleware. It simply says:

"I'm done. Whoever is next, please continue."

This makes middleware reusable and allows ASP.NET Core to build the pipeline dynamically.

The one mental model I'd remember

Imagine each middleware is a relay race runner.

Runner 1 (Logging)
        |
        | passes baton (_next)
        v
Runner 2 (Authentication)
        |
        | passes baton (_next)
        v
Runner 3 (Authorization)
        |
        | passes baton (_next)
        v
Finish Line (Endpoint)
The baton is the HttpContext (the request/response information).
The instruction to pass it on is await _next(context).
After the finish line is reached, the runners metaphorically "run back" in reverse order, allowing each middleware to do post-processing (like logging the response, adding headers, or measuring elapsed time).

Once you think of middleware as a chain of runners passing the same baton forward and then observing the result on the way back, the design of ASP.NET Core's middleware pipeline becomes much more intuitive.
